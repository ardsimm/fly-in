# Parser: subject violations, accepted invalid maps, and misleading errors

## Summary

Stress testing the parser (report `claude/reports/report_0_20260925-031836.md`, section 8)
found maps that the subject (chapter VII.4) says must be rejected but are accepted, one
valid zone type that is rejected, and several inputs that give a crash or a misleading error.
Each case has a reproduction map in `data/maps/claude/parser/` (or `solver/`). Run it with:

```sh
make run MAP=data/maps/claude/parser/<map>.txt
```

Code under test: commit `fe813e0`. All line numbers refer to `src/parser/parser.py`.

## Subject violations

### 1. `zone=blocked` is rejected

- Map: `parser/01_blocked_zone.txt`
- Actual: `Invalid zone blocked, options:['normal', 'restricted', 'priority']`
- Expected: `blocked` is one of the four valid zone types (subject VI). The map must parse, and
  drones must never enter the zone.
- Cause: the default `allowed_values` in `__extract_zone` (line 165) omits `blocked`.
  `__map_priority` already maps it to `-1`.
- Follow-up: `Simulation.bfs` / `check_solvable` and `cooperative_bfs` do not skip blocked
  zones yet, so a blocked zone becomes routable once it parses.

### 2. Capacity `0` is silently accepted as `1`

- Maps: `parser/02_max_drones_zero.txt`, `parser/03_link_capacity_zero.txt`
- Actual: both maps solve normally, with the capacity treated as 1.
- Expected: `max_drones` and `max_link_capacity` must be positive integers (VII.4), so `0` is
  a parse error.
- Cause: `metadata.get(...) or 1` (lines 183 and 410) turns `0` into `1` before the range check
  runs. The `max_drones` check is also `< 0` (line 185) instead of `< 1`.

### 3. `nb_drones: 0` is accepted, then crashes

- Map: `solver/08_zero_drones.txt`
- Actual: parsing succeeds, then `get_turns` raises
  `ValueError: max() iterable argument is empty` and a traceback is printed.
- Expected: parse error, because `nb_drones` must be a positive integer (VII.4).
- Cause: `__parse_nb_drones` checks `n < 0` (line 296) instead of `n < 1`.

### 4. Duplicate zone names are accepted

- Maps: `parser/04_hub_named_like_start.txt`, `parser/05_hub_named_like_end.txt`,
  `parser/36_start_end_same_node.txt`
- Actual: 04 solves (both `start` zones exist). 05 and 36 fail later with
  `Error: map is not solvable`, which points at the wrong problem.
- Expected: "Each zone must have a unique name" (VII.4), so a parse error on the second
  definition.
- Cause: `node_names` (line 518) is only filled and checked for `hub:` lines (lines 539-544).
  `start_hub:` and `end_hub:` names never go into it, and are never compared with each other.

### 5. Lines with an unknown prefix are silently ignored

- Maps: `parser/06_unknown_line.txt` (`hubb: a 1 0`), `parser/24_tab_separated.txt`
  (`hub:<TAB>a...`), `parser/33_no_space_after_colon.txt` (`hub:a 1 0`)
- Actual: the line is dropped without an error. In 06 the map still solves, just without zone
  `a`. In 24 and 33 the error only appears later, as `Hub name a is invalid` on a connection
  line.
- Expected: "The input file must respect the expected structure and syntax", and any parsing
  error must stop the program with the line and the cause (VII.4). The bad line itself should
  be reported.
- Cause: the `if/elif` chain in `parse` (lines 523-545) has no `else` branch.

## Crash and false error

### 6. Self-loop connections (`a-a`)

- Maps: `parser/35_self_loop_last.txt`, `parser/34_self_loop_first.txt`,
  `solver/09_self_loop.txt`
- Actual:
  - With the self-loop last: parsing succeeds, then `cooperative_bfs` raises `StopIteration`
    and a traceback is printed. The generator
    `next(iter(connected_node ... if connected_node != current_node))` has no default.
  - With the self-loop first: every later connection on that zone is rejected as
    `Duplicated connection:start-a`. The duplicate check (lines 553-554) tests whether both
    names of the *known* connection appear in the new one, and `a-a` has only one distinct
    name.
- Expected: reject `a-a` with a clear parse error. The subject does not define self-loops,
  and they are meaningless for routing.

## Weaker issues

### 7. Duplicate metadata keys are accepted

- Map: `parser/07_duplicate_metadata_key.txt` (`[max_drones=1 max_drones=5]`)
- Actual: accepted, and the last value wins.
- Expected: a parse error, since the metadata block is ambiguous.

### 8. The coordinate error always says "y"

- Map: `parser/23_float_coords.txt` (`hub: a 1.5 0`)
- Actual: `Parsing error: invalid value: 1.5 for hub y`, although the bad value is `x`.
- Cause: the message is hard-coded in `__parse_coordinate` (line 215).

### 9. Start and end hubs listed twice in "options"

- Maps: `parser/09_connection_before_hub.txt`, `parser/27_unknown_hub_in_connection.txt`
- Actual: `options: [start, a, goal, start, goal]`
- Cause: `nodes` already contains the start and end hubs, and `known_nodes` appends them again
  (lines 546-550).

### 10. No line numbers in error messages

The messages quote the offending line but do not give its number. The subject asks for "a
clear error message indicating the line and cause". Quoting the line probably counts, but a
number helps on large maps (the challenger map has 189 lines). Errors raised after the loop,
such as `Missing end hub`, have no line to point at, which is fine.

### 11. Leftover debug prints

`print(metadata)` (line 182) and `print(hub_metadata)` (line 264) print every metadata block
while parsing.

## Checklist

- [ ] Accept `zone=blocked`; make `bfs` / `cooperative_bfs` never enter blocked zones
- [ ] Reject `max_drones=0` and `max_link_capacity=0` (check the value before any default is applied)
- [ ] Reject `nb_drones: 0`
- [ ] Enforce unique names across `start_hub`, `end_hub` and `hub` lines
- [ ] Raise a parse error on any line with an unknown prefix
- [ ] Reject self-loop connections (`a-a`)
- [ ] Reject duplicate metadata keys
- [ ] Name the correct coordinate (`x` or `y`) in the coordinate error
- [ ] Remove the duplicate start/end entries from the "options" list
- [ ] (Optional) Include line numbers in parse errors
- [ ] Remove the debug prints at lines 182 and 264
- [ ] Re-run every map in `data/maps/claude/parser/` and check it against the "Expected" column in `data/maps/claude/README.md`

# Unhandled exceptions: 4 inputs end in a Python traceback

## Summary

The subject says: "If your program crashes due to unhandled exceptions during the review, it
will be considered non-functional." The top-level `except Exception` in `src/__main__.py`
prevents a hard crash, but it prints "An unhandled exception occured:" and a full traceback,
which a reviewer will read as a crash. Four inputs reach it. Found during the audit in
`claude/reports/report_3_20260929-041535.md` (section 6.1).

## Cases

### 1. Map file that is not valid UTF-8

`src/__main__.py:26-30` only catches `OSError`. `file.read()` raises `UnicodeDecodeError`
(a `ValueError`) on a binary or Latin-1 file.

```sh
printf '\xff\xfe\x00bad\n' > /tmp/bin.txt
uv run python -m src /tmp/bin.txt
# UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 0
```

### 2. `zone=blocked` on the start hub

The parser accepts any zone type on `start_hub`. The solver produces paths that start in a
blocked zone, and `Simulation.get_turns` raises `InvalidMoveError("Invalid move D0:s: node is
blocked")` for step 0 (`simulation.py:380`). `Main` catches `InvalidMoveError` only around
`check_solvable` (line 44), which never raises it; the `get_turns` call at line 51 is only
guarded for `PathNotFoundError`.

```
nb_drones: 2
start_hub: s 0 0 [zone=blocked]
hub: a 1 0
end_hub: g 2 0
connection: s-a
connection: a-g
```

Choose a rule (reject blocked/restricted on start, or ignore the zone on start/end) and
catch `InvalidMoveError` wherever `get_turns` is called.

### 3. Visualiser: coordinate spread larger than the window

`Visualiser.__compute_node_bounding_rect` (`visualiser.py:34-42`) returns
`floor(window_width / (max_x + 1))`. When the spread of x (or y) reaches the window size in
pixels, the result is 0 and `CoordinateManager.get_paddings` divides by it
(`coordinate_manager.py:31`): `ZeroDivisionError`. On the test display (window 819x614), a map
with `max_x = 819` crashes and `max_x = 818` works.

```
nb_drones: 2
start_hub: s 0 0
hub: a 500000 0
end_hub: g 1000000 0
connection: s-a
connection: a-g
```

Scaling to the bounding box with a float cell size (and a minimum node radius) avoids both the
crash and the 1-pixel nodes.

### 4. Visualiser: fallback color dict contains an invalid color

`data/colors.json` is opened with a relative path (`color_manager.py:28`). When the program is
started from another directory, `BORING_BACKUP_DICT` is used. It maps `"mauve"` to `"mauve"`,
which pygame does not know: `ValueError: invalid color name` in `NodeElement.draw`.

```sh
cd /tmp && uv run --project <repo> python -m src <repo>/map_with_mauve.txt
```

Resolving the path from `__file__` and wrapping the color conversion (fall back to a default on
`ValueError`) fixes both halves.

### Latent: failure path after `PathNotFoundError`

If `cooperative_bfs` raises `PathNotFoundError`, `Main` prints "Failed to find solution" and a
traceback to stdout. At HEAD it then calls `get_turns_with_waits({})`, where `max([])` raises
`ValueError` (`simulation.py:307`). In the working tree it returns 0 (success). Not triggered on
12,500 random maps, but the handler should print a clean message to stderr and return 1.

## Checklist

- [ ] Catch `UnicodeDecodeError` (or `ValueError`) when reading the map file
- [ ] Decide what `zone=blocked` / `zone=restricted` means on start and end hubs, and implement it in the parser
- [ ] Catch `InvalidMoveError` around `get_turns` in `Main`
- [ ] Remove the dead `except InvalidMoveError` around `check_solvable`
- [ ] Visualiser: never compute a cell size of 0; scale to the bounding box
- [ ] Resolve `data/colors.json` relative to the source file, not the current directory
- [ ] Remove `mauve` from `BORING_BACKUP_DICT` and guard every color conversion
- [ ] On `PathNotFoundError`: message on stderr, no traceback, exit 1, do not open the visualiser
- [ ] Re-run `data/maps/claude/parser/` and the maps above; none may print a traceback

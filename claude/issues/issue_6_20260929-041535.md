# Solver time and memory grow quadratically with the number of drones

## Summary

VII.4: "The program must be able to handle any number of drones." VII.1 asks "Can it work
with a large number of drones?" and "How does it impact memory usage?". On a 3-zone chain,
runtime and memory grow as O(N^2). Found during the audit in
`claude/reports/report_3_20260929-041535.md` (section 6.6).

## Measurements

| Map | Drones | Turns | Time | Peak RSS |
|---|---|---|---|---|
| chain s-a-b-g | 1,000 | 1,002 | 0.75 s | 30 MB |
| chain s-a-b-g | 5,000 | 5,002 | 21.0 s | 133 MB |
| chain s-a-b-g | 20,000 | - | > 590 s (killed) | 1.2 GB at kill |
| grid 60x60, random caps | 300 | 419 | 13.7 s | 125 MB |

The provided maps all run in well under a second.

## Causes (cProfile, 5,000-drone chain)

1. **Every waiting turn is a search state and a path entry.** Drone k waits about k turns in
   the start zone. Each waiting turn is pushed, popped and expanded, so the search costs
   O(k) per drone and O(N^2) overall. Every waiting turn is also stored in `drone.path`:
   12.5 million entries for 5,000 drones (N^2 / 2).
2. **`current.connections.sort(...)` on every pop** (`simulation.py:133-141`): 12.5 million
   sorts, about 25% of the runtime. The order depends only on neighbour priorities, which never
   change; sort once after parsing. It also mutates the map during solving.
3. **`get_turns` / `get_turns_with_waits`** iterate over all drones for every turn: O(N x T).

## Possible directions

- Waiting in the start zone does not need to be simulated turn by turn: compute the earliest
  turn at which the first move out of the start is free (for example, scan the reservation
  table for the start links and neighbours), and start the search there.
- Store paths as (departure turn, list of moves) instead of one entry per turn.
- Build the per-turn move lists from each drone's moves directly (O(total moves)).

## Checklist

### `FontManager.get_font` does not cache

```python
return cls.fonts.setdefault((name, size), pygame.font.Font(name, size))
```

Python evaluates the arguments of `setdefault` before calling it, so a new `Font` is built on
every call even when the key exists. Measured: 4,200 `Font` constructions in 300 frames on
`easy/02` (14 per frame), 422,400 on the 1,000-drone grid. Frame rate is acceptable anyway
(127 fps on the challenger map, uncapped), but a reviewer reading the code will spot it.
Fix: `if key not in cls.fonts: cls.fonts[key] = pygame.font.Font(name, size)`, then return
`cls.fonts[key]`.

## 5. The two-line fix for the medium maps

Both suboptimal maps have the same cause: a drone waits for the previous one to finish
landing before taking off on a restricted connection. In `circular_loop`, the
`loop_b-exit_point` link then serves one drone every 2 turns instead of every turn. Two
checks in `cooperative_bfs` cause it:

1. **In-flight position counted as link occupancy** (reservation, `simulation.py:277`). The
   in-flight step is reserved at turn t+1 under the connection key. A drone departing at
   t+1 reads that key as link occupancy, so it is refused. v2.0 says the connection is free on
   the landing turn. The take-off is still counted through `current_connection` at turn t,
   so this reservation only needs to be skipped:

   ```python
   if current_step is not None and not isinstance(current_step, Connection):
   ```

2. **Zone capacity checked on the in-flight turn** (`simulation.py:165`, report 2's F3). For a
   restricted destination, the general check compares its occupancy at t+1 (while the drone
   is in the air) with its capacity. Only the landing turn t+2 matters, and it has its own
   check further down. Skip the t+1 comparison for restricted destinations:

   ```python
   or (
       next_node_occupency >= next_node_capacity
       and next_node.priority != NodePriority.restricted.value
   )
   ```

## 6. Solver optimisation advice

In order of value for the grade, then for the defense.

### 6.1 Apply section 5 first

Two conditions, verified, and all 10 graded maps at their optimum. Nothing else on this list

### 6.2 Know the limits of prioritized planning (defense)

The solver is prioritized planning: each drone takes its earliest-arrival path given the
reservations of the drones before it. It is greedy: no drone ever gives up a turn to help the
others. On the graded maps this is optimal (after section 5), but it is not in general.
Hand-made counter-examples (optimum computed by time-expanded max-flow, report 0):

| Map | Result | Optimum | Why |
|---|---|---|---|
| `claude/solver/01_braess_cross` | 42 | 23 | every drone takes a shortcut that congests the shared lane |
| `claude/solver/02_selfish_detour` | 29 | 16 | no drone takes a detour that is 2 turns longer for itself but frees a capacity-1 door |
| `claude/solver/03_tie_break` | 4 | 3 | a tie is broken by file order, and the first drone blocks the second |

"Evaluation maps may be different": be ready to explain this, or pick one of the options below.

### 6.3 If you want optimality in general: max-flow on a time-expanded graph

Since drones are identical and all start at the same place, "all drones delivered in T turns"
is a **flow problem**:

- Build a time-expanded graph for a horizon T: one copy of each zone per turn.
- **Zone capacity**: split each zone copy into `in -> out` with capacity `max_drones`. Start and
  end copies are uncapped.
- **Waiting**: edge `zone(t).out -> zone(t+1).in`.
- **Moves**: through a node per (connection, t) with capacity `max_link_capacity`, which both
  directions share (that makes the link capacity undirected).
- **Restricted destination**: `A(t) -> link(t) -> R(t+2)`. The link node has a single outgoing
  edge, so a drone cannot wait in the air. Under v2.0, it only uses the link at turn t, which
  matches the rule.
- **Blocked zones**: left out.
- Find the smallest T whose max flow from `start(0)` to the end copies is `nb_drones`.
  Increase T one by one (or binary search), starting from the shortest path length. Then
  decompose the flow into one path per drone.

This gives the exact optimum on every map, including the three above. It is hand-written
(Edmonds-Karp or Dinic, no library), so it stays within the rules. Cost: the graph has
O(T x (V + E)) nodes. For the graded maps (T <= 43, a few dozen zones) that is small, but
for large drone counts, T grows with N. A practical approach is to keep the current solver as
the default and add the flow solver as an "exact" mode for small maps, or to use the current
result as the upper bound for T.

Cheaper middle ground (the classic lem-in technique): compute k shortest disjoint paths
(Suurballe / successive shortest paths with node splitting), then assign n_i drones to path i
so as to minimise max(len_i + n_i - 1). This handles 6.2's first two maps well, but not
capacities > 1 or restricted timing as cleanly.

### 6.4 Improvements inside the current design

- **Iterative repair**: after the first pass, remove one drone's reservations, replan it, keep the
  change if the makespan does not grow. Repeat until stable. This often fixes the "selfish"
  cases without a new algorithm.
- **Multiple orderings or tie-breaks**: all drones are identical, so ordering does not matter.
  Tie-breaking between equal-time routes does. Try a few tie-break policies (priority first,
  least-reserved link first, random with a seed) and keep the best schedule. It is cheap, since
  the solver is fast on graded maps.
- **Visited per (node, time) instead of per node**: the current `visited` set allows each zone
  only once per drone search, plus waits. This makes the search incomplete (a zone reached
  early but blocked afterwards cannot be re-entered later), and it is why the special wait
  rules exist (`len(connections) > 1`, `not all_visited`). With `(node, turn)` states and a
  horizon bound, the search becomes a true space-time A* and those rules can go.
- **Heuristic**: pre-compute the distance to the goal from every zone once (reverse BFS, with
  2-turn cost for restricted), and use it as an A* heuristic. It reduces expanded states a lot on
  large maps.

### 6.5 Speed and memory (not graded, but asked in VII.1)

Unchanged since report 3: O(N^2) in the number of drones on bottleneck maps, because every
waiting turn is a heap state and a stored path entry (5,000 drones on a chain: about 20 s).
Two changes remove most of it:

- Do not simulate waiting in the start zone. For drone k, start the search at the first turn
  where a move out of the start is possible (scan the reservation table), and store paths as
  (departure turn, moves).
- Build the per-turn lists from each drone's moves (O(total moves)) instead of looping over all
  drones for every turn.

Since speed is not graded, it is enough to describe the complexity honestly in the README.

# Report 0 - Solver and parser stress test

Date: 2026-09-25. Code under test: commit `fe813e0` ("wip: node & connection capacities"),
visualiser disabled in `src/__main__.py`. Restricted zones are not supported yet and were left
out of every new map. On the provided maps that contain them, `restricted` is currently treated
as a normal 1-turn zone. The optimal values below assume the same thing.

## 1. Summary

| Area | Verdict |
|---|---|
| Validity of schedules (zone and link capacities, adjacency, delivery) | **Solid.** 0 invalid schedules over 103,600 random maps + all hand-made maps |
| Solver crashes / infinite loops | None in the solver itself |
| Optimality | Optimal on all provided maps except `custom/fast_path_trap` (+2). Around 3% of random maps are suboptimal, **up to +19 turns (42 vs 23)** on crafted traps |
| Priority zones | **Inverted**: priority zones are explored last, restricted zones first |
| Parser | 4 subject violations (blocked zones rejected, capacity 0 accepted, duplicate names accepted, unknown lines ignored), 1 crash, 1 false error |
| Program-level crashes | `nb_drones: 0` and a self-loop connection both end in a traceback |
| Output | Not in the subject format, turn count off by one, huge debug output (2.1 GB for 1000 drones) |
| Performance | 1000 drones on a 144-zone grid: 10 s of solving, 22 s end-to-end due to printing |

## 2. Method

A harness (kept outside the repo, in the session scratchpad) imports `Parser` and `Simulation`
directly, runs `check_solvable`, `cooperative_bfs` and `get_turns` with stdout silenced and a
timeout, then:

1. **Validates the paths independently of the program.** Every drone starts at the start hub,
   ends at the end hub and does not reach it earlier. Every step is a wait or a move along an
   existing connection. At every turn, zone occupancy is at most `max_drones` (start and end
   excluded) and link usage is at most `max_link_capacity`, counting both directions.
2. **Computes the true optimum** with a time-expanded max-flow. Each zone at each turn becomes a
   node with capacity `max_drones`, each connection at each turn becomes a node with capacity
   `max_link_capacity` shared by both directions, and waits are free. The smallest horizon T
   whose max-flow reaches `nb_drones` is the optimal number of turns. This model allows exactly
   the moves the subject allows, so it is a true optimum rather than a bound.
3. **Fuzzes** random connected maps: 4-30 zones, random `max_drones` in {1,2,3}, link capacities
   in {1,2,3}, some priority zones, 1-40 drones.
4. **Shrinks** each suboptimal map automatically: it removes zones and links, lowers capacities
   and drone counts, and keeps the smallest map that still shows the same gap. The trap maps in
   `data/maps/claude/solver/` come from this step, renamed and commented.

The real CLI (`python -m src <map>`) was also run on every map to check exit codes, messages
and tracebacks.

Terminology: **turns** below means the number of moves made by the last drone. The program
prints `Solution found in N turns` with N = turns + 1 (see section 7).

## 4. Validity: no violations found

- 3,600 random maps with the optimum computed, plus 100,000 random maps checked for validity
  only (small dense graphs with many drones and capacity-2 zones, chosen to provoke conflicts).
- **0 invalid schedules, 0 solver crashes, 0 timeouts.**
- All 15 hand-made solver maps are valid, including dead-end pockets (no drone ever enters one),
  a 50-drone single link, and 1000 drones on a grid.

The reservation table (`allocation_table[turn] = (zone occupancy, link usage)`) is used
correctly. Occupancy is checked at the arrival turn, so a drone leaving a zone frees the space in
the same turn, as the subject requires. Link usage is shared by both directions, and the end
zone is limited only by its links.

### Latent risk (not triggered)

When a drone waits (`prev_nodes[(turn, current_node)] = (current_node, None)`), the occupancy
of `current_node` at `turn + 1` is **not checked**. The schedule would be invalid if a drone
planned earlier arrives in that zone on that same turn. I could not produce this in 103,600
maps, and I believe it is currently almost unreachable: each drone is planned against a
superset of the previous drones' reservations, so a later drone practically never reaches a
zone before an earlier drone that arrives there on the following turn. That reasoning depends on
the current planner, though. Re-planning, reordering drones, or adding 2-turn restricted moves
could expose it, and `get_turns` would then raise an uncaught `InvalidMoveError`. `get_turns`
also never checks link capacity, so it would not catch a link overflow at all.

## 5. Optimality

Fuzzing results (turns above the optimum):

| Set | Maps | Optimal | +1 | +2..+5 | +6 and more |
|---|---|---|---|---|---|
| 4-14 zones, 1-12 drones | 1500 | 1456 | 32 | 12 | 0 |
| 4-7 zones, 1-30 drones | 1500 | 1482 | 2 | 12 | 6 |
| 12-30 zones, 1-40 drones | 600 | 542 | 24 | 23 | 11 |

The algorithm is **prioritized planning**. Drones are planned one after the other, and each
takes its own earliest arrival given the reservations of the drones planned before it. Nothing
is ever re-planned. This is fast and always valid, but each drone optimizes only itself, which
fails in three identifiable ways.

### 5.1 Selfish routing (worst gaps)

`solver/02_selfish_detour.txt`: **29 turns vs 16 optimal** (28 drones).

A hall (`max_drones=2`) opens onto the goal through a single-capacity door. Beside the door
there is a detour that is 2 moves longer (hall-x-y-goal). For any individual drone, waiting one
turn in the hall is better than the detour, so no drone ever takes it:

```
D0: start hall goal
D1: start hall hall goal
D2: start start hall hall goal
D3: start start start hall hall goal
...
```

The door carries 1 drone per turn, while door plus detour could carry 2. The queue sits at the
start hub, where it is invisible to the drone that could have stepped aside.

### 5.2 Braess-style cross link (largest gap found)

`solver/01_braess_cross.txt`: **42 turns vs 23 optimal** (40 drones).

The map has a short lane of 3 moves (start-a-b-goal) and a long lane of 5 moves
(start-c-d-e-f-goal), plus a cross link a-c. Every drone after D0 finds that start-c-a-b-goal
arrives no later than anything else, so each one goes through `c` and then merges into the
short lane:

```
D0: start a b goal
D1: start c a b goal
D2: start start c a b goal
...
```

`c` is occupied on every turn, so the long lane is never used and all 40 drones go through
`b` one per turn. The optimum ignores the cross link and runs both lanes in parallel. Your
`custom/fast_path_trap.txt` (20 vs 18) is a smaller case of the same pattern: drones wait
three turns in `c` (`a c c c m goal`) while the `g-h-i-n-z` lane is under-used.

### 5.3 Tie-breaking without look-ahead

`solver/03_tie_break.txt`: **4 turns vs 3 optimal** (3 drones).

D1 can choose between two 3-move routes, start-b-a-goal and start-b-c-goal. It picks the one
through `a`, which is the only other short route for D2. Which route it picks depends on
connection order in the file and on the priority sort.

### Possible directions (not implemented)

- Measure the problem as a flow first: max-flow / min-cost-flow on the time-expanded graph (the
  model used by this harness) gives the optimal number of turns. It can then either drive the
  routing directly (decompose the flow into paths) or serve as a target to compare against.
- Keep prioritized planning, but make the choice collective. For example, find the smallest T
  for which all drones fit, then plan each drone to arrive by T rather than as early as
  possible. Or try several drone orders and route choices and keep the best result.
- Break ties by the remaining congestion on a route, not by file order.

## 6. Priority zones are inverted

The parser maps zone types to `Node.priority` as blocked=-1, restricted=0, normal=1, priority=2.
`cooperative_bfs` sorts connections by that value **ascending**
(`src/simulation/simulation.py:118`), so for equal lengths the BFS reaches restricted zones
first and priority zones last.

`solver/04_priority_tie.txt` (two 2-move routes, one through `fast_lane [zone=priority]`):

- as written: the drone goes through `slow_lane`
- with the two start connections swapped in the file: still `slow_lane`
- with `fast_lane` changed to `zone=restricted`: the drone now goes **through** it

Once restricted zones cost 2 turns this matters less, because the BFS will handle their timing.
But priority zones will still lose every tie.

## 7. Program-level issues

### Crashes (traceback on stderr, exit 1)

| Map | Cause |
|---|---|
| `solver/08_zero_drones.txt` | `nb_drones: 0` is accepted (`__parse_nb_drones` only rejects `< 0`). `get_turns` then calls `max([])`: `ValueError: max() iterable argument is empty` |
| `parser/35_self_loop_last.txt` | `connection: a-a` is accepted. In `cooperative_bfs`, `next(iter(... if connected_node != current_node))` has no default, so `StopIteration` is raised on that connection |

`PathNotFoundError` from the per-drone reconstruction (`simulation.py:216`) is also outside any
try block in `main`. I never saw it raised on a solvable map, but if it were raised it would end
in a traceback rather than a clean message.

### Output

- **Turn count off by one**: `get_turns` emits one step per path index, and index 0 is the
  initial state (all drones on the start hub). `Solution found in N turns` always prints the
  optimum + 1 on optimal maps. For example, easy/01 prints 5 for a 4-turn solution.
- The format is not the subject's `D<ID>-<zone>` space-separated line per turn. Drones that
  wait are listed although the subject says to omit them, and delivered drones are not treated
  specially.
- Drone ids are 0-based (`D0`), while the subject's examples start at `D1`. `Drone.name` already
  holds `D1..`, but the printing code uses `id`.
- **Debug output volume**: `cooperative_bfs` prints the whole allocation table after every drone,
  which is O(drones x turns x zones) lines. Stdout sizes: 292 KB for 40 drones, 90 MB for 200
  drones on the grid, **2.1 GB** for 1000 drones. The parser also prints every metadata block
  (`parser.py:182`, `parser.py:264`), and `bfs` prints every predecessor.

## 9. Performance

Solver time with printing disabled (monkeypatched `print`), compared with the real CLI:

| Map | Zones | Drones | `cooperative_bfs` | CLI end-to-end | stdout |
|---|---|---|---|---|---|
| challenger/01 | 54 | 25 | 0.01 s | < 0.1 s | - |
| parser/28_nb_drones_huge | 3 | 5000 | 0.42 s | 1.0 s | 55 MB |
| solver/14_grid_200_drones | 144 | 200 | 0.53 s | 1.1 s | 90 MB |
| solver/15_grid_1000_drones | 144 | 1000 | 10.1 s | 22.4 s | 2.1 GB |

Going from 200 to 1000 drones on the same grid multiplies solving time by about 19, which is
close to quadratic in the drone count. That fits O(drones x turns x zones): each drone runs a
BFS over (turn, zone) states, and the number of turns grows linearly with the number of drones.
The 1000-drone grid result (521 turns) is optimal: only 2 single-capacity cells touch the start,
so the last drone cannot leave before turn 500, and it needs 21 more moves after that.

## 10. Other observations from reading the code

- `simulation.py:2` imports `from tkinter import Entry`, which is unused. It fails at import
  time on a Python build without Tk, and flake8 reports it (F401).
- `visited` is per zone, not per (turn, zone). A drone can never come back to a zone except by
  waiting in it, so paths that step aside and return are impossible. The fuzzing found no case
  where this alone cost turns, but it combines with the latent wait issue in section 4.
- A drone cannot wait in a zone with a single connection (`len(current_node.connections) > 1`),
  or once all its neighbours are visited. This had no visible effect in testing.
- `current_node.connections.sort(...)` sorts the node's list in place during every expansion,
  which also changes the order `bfs` and the visualiser see.
- `check_solvable` / `bfs` will need to skip blocked zones once they parse.

## 11. Suggested order of work

1. Parser subject violations: blocked zones, capacity 0, duplicate names, unknown lines, and
   self-loops (reject them). These are cheap and reviewers will test them.
2. Crash-proofing: `nb_drones: 0`, and a `try` around `cooperative_bfs` / `get_turns` in `main`.
3. Output: the `D<ID>-<zone>` format, omit waiting drones, fix the off-by-one turn count, and
   put the debug prints behind a flag.
4. Fix the priority sort direction.
5. Restricted zones (2-turn moves, in-flight `D<ID>-<connection>` output). Then re-run this
   suite, since the wait-capacity risk in section 4 becomes more relevant.
6. Optimality: section 5 directions, using `solver/01`-`03` and `custom/fast_path_trap` as
   regression maps.

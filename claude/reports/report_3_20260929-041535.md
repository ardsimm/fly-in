## 2. Method

Everything below was run from the repo root with the project's `.venv` (Python 3.12.13,
pygame-ce 2.5.8). Test tools are in the session scratchpad, not in the repo:

- `validator.py`: an independent re-implementation of the subject rules, written from the
  subject only (it imports no project code). It reads the map and the program's stdout and
  replays each line as one turn. It checks: adjacency, blocked zones never entered, restricted
  zones entered only through one in-flight turn on the connection (`D<ID>-<a>-<b>`), a drone in
  flight always lands on the next turn, zone capacity after each turn (start and end
  excluded), link capacity per turn (a flight counts on its link for take-off and landing), and
  all drones delivered.
- `fuzz.py`: generates random connected maps with normal, priority, restricted and blocked
  zones, random `max_drones` and `max_link_capacity` in 1..3, sometimes a restricted end hub.
  It runs `Main.main` in-process and sorts each run into: valid, invalid schedule, false "no
  solution", or exception.
- `drive_vis.py`: runs the visualiser as HEAD's `Main` does, under `SDL_VIDEODRIVER=dummy`,
  feeds scripted key presses (arrows, space, `r`, up/down, mouse motion) and quits after N
  frames.
- 30 hand-written edge-case maps (`edge/`), large chain and grid maps for scaling.
- A clean export of HEAD (`git archive HEAD`) for lint and output checks, so the working tree
  was never modified.
- `/usr/bin/python3.10` (3.10.12) for the version check.

## 6. Findings

### 6.1 Crashes (issue_1)

Each of these ends with "An unhandled exception occured:" and a Python traceback, exit 1:

1. **Non-UTF-8 map file.** `__main__.py:26-30` catches `OSError` only. A binary or
   Latin-1 file raises `UnicodeDecodeError` (a `ValueError`).
2. **`zone=blocked` on the start hub.** The parser accepts it. `get_turns` then raises
   `InvalidMoveError("... node is blocked")` for step 0 (`simulation.py:380`), and `Main` only
   catches `InvalidMoveError` around `check_solvable` (`__main__.py:44`), which never raises
   it. The `get_turns` call at line 51 is only guarded for `PathNotFoundError`.
3. **Visualiser, wide maps.** The cell size is `floor(window_width / (max_x + 1))`
   (`visualiser.py:34-42`). When the x or y spread reaches the window size in pixels (819 on
   the test display, 4/5 of the screen), it becomes 0, and `CoordinateManager.get_paddings`
   divides by it (`coordinate_manager.py:31`): `ZeroDivisionError`. Reproduced with
   `max_x = 819`; `818` works but every node is 1 pixel wide.
4. **Visualiser, fallback colors.** When `data/colors.json` cannot be read (program started
   from another directory, since the path is relative), `BORING_BACKUP_DICT` is used. It maps
   `"mauve"` to `"mauve"`, which pygame rejects: `ValueError: invalid color name` in
   `NodeElement.draw`. Reproduced by running from `/tmp` with a `color=mauve` hub.

Latent (not triggered, but reachable in principle):

- If `cooperative_bfs` raises `PathNotFoundError`, `Main` prints "Failed to find solution" and a
  traceback to stdout. HEAD then calls `get_turns_with_waits({})`, and `max([])` raises
  `ValueError` (`simulation.py:307`). The working tree returns 0 instead, i.e. exit status
  "success" after a failure.
- `KeyboardInterrupt` is handled, but only in the `__main__` block. That is fine as long as
  `Main.main` is only called from there.

### 6.2 Python version (issue_2)

Checked with a real 3.10.12 interpreter: `parser.py`, `node.py`, `simulation.py` and
`node_element.py` fail to parse ("unterminated string literal"), and `from enum import
StrEnum` fails. On 3.11, `StrEnum` exists but the f-strings still fail. The effective minimum
is 3.12. Two ways out: keep 3.12 and declare `requires-python = ">=3.12"` (still satisfies
"3.10 or later"), or rewrite the 8 f-strings and replace `StrEnum`. The first is one line; the
second is more portable. `typing_extensions` is imported in 8 files but is not a declared
dependency; it is only installed transitively (through mypy/pydantic).

### 6.5 Parser messages (issue_5)

Behaviour is correct (every malformed map is rejected, every valid one accepted), but the
messages are uneven:

| Input | Message | Problem |
|---|---|---|
| `max_drones=0` | `Invalid max drones 0:max_drones must be am integer >= 1` | no line, typo "am", missing space |
| `[speed=9]` | `Parsing error: invalid metadata: [speed=9]` | no line |
| `hub: a 1.5 0` | `invalid value: 1.5 for hub coordinate` | no line, does not say x or y |
| `hub: a-b 1 0` | `Invalid name a-b:names cannot ...` | no line |
| `connection: a-a` | `This implementation does not accept self-loops (a-a)` | no line |
| second `start_hub` | `File must only contain one start_hub` | no line |
| duplicate metadata key | `Error in line "max_drones=1 max_drones=5"` | quotes the metadata, not the line |
| `hubb: a 1 0` | `Invalid line prefix "fhubb"` | stray `f` (`parser.py:592`: `\"f{` inside an f-string) |
| line with no `:` | `An unhandled error occured while parsingline: "...": substring not found` | `line.index(':')` raises `ValueError`; caught by the generic handler; missing space |
| UTF-8 BOM at file start | `First line must be nb_drones` | confusing; could strip `﻿` |
| `nb_drones:5` / `hub:a 1 0` | `First line must be nb_drones` / `Invalid line prefix "fhub"` | a space after `:` is mandatory; acceptable, but the message should say so |

No message contains a line number. Since `__strip_lines` drops blank and comment lines before
parsing, the original line numbers are lost; keeping `(number, text)` pairs would fix every row
above at once.

### 6.6 Performance (issue_6)

| Map | Drones | Turns | Time | Peak RSS |
|---|---|---|---|---|
| chain s-a-b-g | 1,000 | 1,002 | 0.75 s | 30 MB |
| chain s-a-b-g | 5,000 | 5,002 | 21.0 s | 133 MB |
| chain s-a-b-g | 20,000 | - | > 590 s (killed) | 1.2 GB at kill |
| grid 30x30, random caps | 300 | 209 | 2.3 s | 39 MB |
| grid 60x60, random caps | 300 | 419 | 13.7 s | 125 MB |
| `claude/solver/15_grid_1000_drones` | 1,000 | 521 | 1.6 s | - |

Cause (cProfile on the 5,000-drone chain, 60 s under the profiler):

- Drone k waits about k turns at the start, and every waiting turn is a separate heap state,
  popped and expanded. Total work is sum(k) = O(N^2). The stored paths also include every
  waiting turn: 12.5 million path entries for 5,000 drones (N^2 / 2), which is where the
  memory goes.
- `current.connections.sort(...)` runs on every pop (`simulation.py:133-141`): 12.5 million
  sorts, 25% of the runtime. The order never changes; it could be sorted once after parsing.
- `get_turns` and `get_turns_with_waits` loop over every drone for every turn: O(N x T).

For the provided maps this is irrelevant (all run in well under a second). It matters for
"the program must be able to handle any number of drones" and for the complexity questions in
VII.1.

### 6.7 Visualiser (issue_7)

Works on every provided map, including stepping back and forth, auto-play, speed change and
reset. Gaps that matter for "quality and usefulness of visual representation":

- `gray` and `darkred` (used in the provided maps) are missing from `colors.json`; lookups are
  case-sensitive with no fallback to pygame's own color names, so those zones are black.
- Connection color depends only on `connection.nodes[1]` (`connection_element.py:62-83`), so
  `a-r` and `r-a` are drawn differently. Zone type is never shown on the node itself.
- No drone IDs, no turn counter, no on-screen help for the keys, no indication of delivered
  drones.
- One integer coordinate unit is one cell, so sparse maps get tiny: `max_x = 100` gives 8 px
  cells and 2 px node radii (and the crash at the window width, 6.1).
- A new `pygame.font.Font` is created for every node and connection on every frame.

### 6.8 Housekeeping (issue_8)

- Working tree: the visualiser call is commented out and flake8 fails. Do not submit that
  state; keep the `turns[1:]` change.
- `Makefile:56`: `.phony` must be `.PHONY`. `Makefile:43`: `mypy src` instead of the subject's
  `mypy .`. `--exclude=$(VENV),llm_sdk` mentions a directory from another project.
  `$(TEST_NAME)` is never defined.
- `matplotlib` and `pydantic` are declared dependencies but never imported; `black`,
  `flake8`, `mypy` could be dev dependencies.
- `src/graph`, `src/solver`, `src/display` and `src/visualiser/color_palette.py` are unused.
- `Visualiser.__init__` has a mutable default argument (`color_palette = {}`), unused.
- `Main` catches `InvalidMoveError` around `check_solvable`, which cannot raise it.
- Asserts are used for input validation inside the parser (`parser.py:180, 185, 194`) and

## 8. Notes that are not issues

- Validation in `get_turns` replays drones in list order and checks capacity after each
  individual move. A drone listed earlier entering a zone that a later drone leaves on the same
  turn would be flagged falsely. Likewise, a wait in place is not checked against the zone's
  reservation at t+1. With per-drone earliest-arrival search, a later drone cannot reach a zone
  before an earlier one, so neither case can occur; none showed up in 12,500 maps.
- `Connection.__hash__` is order-independent but the dataclass `__eq__` is order-dependent.
  This is harmless because duplicate connections are rejected and connections are compared by
  identity in practice.

# Report 1 - Restricted zones: test results and design diagnosis

Date: 2026-09-27. Code under test: the working tree on top of `90ddbd9`, with
`src/simulation/simulation.py` as edited by the user (including the reconstruction guard for
connections with no restricted end). Test maps: `data/maps/claude/restricted/`. Their expected
results and the three properties (P1, P2, P3) are defined in `data/maps/claude/README.md`.

On 3,000 random maps with restricted zones, 1,552 are OK, 1,250 fail with "Path not found" and

made during the search, and the edit only changed how the path is rebuilt afterwards.

P1 (exactly one turn on the connection) and P2 (land on the next turn) held on every schedule
the solver produced. The P2 failures show up as "Path not found" instead (section 3.1).

## 2. Method

To confirm each suspected cause, I stacked six small changes on copies of the solver in the
session scratchpad (the repo is untouched) and re-ran the maps and fuzzing after each one. Each
change targets a single cause, so the change in results attributes each failure to one cause.

| Step | Change applied to the copy (cumulative) | Restricted maps OK (of 12) | Random maps OK (of 3,000) |
|---|---|---|---|
| baseline | - | 7 (3 path-not-found, 3 P3) | 1,552 |
| E1 | landing check reads turn t+2 instead of t+1 | 7 (**5** path-not-found, 0 P3) | 1,607, 0 P3 |
| E2 | a refused take-off no longer marks the zone visited | 10 | 1,746 |
| E3 | remove the second landing reservation | 10 (08: 9 -> 5 turns) | 1,749 |
| E4 | in-flight destination = the end that is not the origin | 11 (12: 11 -> 9 turns) | 1,804 |
| E5 | stop the search when the drone lands in the goal, not when it takes off | 12 | 3,000 |
| E6 | general zone check skipped for restricted zones (landing check only) | 12, all at expected turn counts | 3,000 (and 3,000 more with another seed) |

After E6, the provided maps are all valid and `challenger/01` solves in 43 turns.

## 3. Design issues

### 3.1 The in-flight state does not know where it is going

A drone in flight is queued as `(turn, idx, None, connection)`, which stores neither its origin
nor its destination. The destination is recomputed on the next expansion as "the first
restricted end of the connection" (lines 212-218). When both ends are restricted, that is
`connection.nodes[0]` whatever the direction of travel. With `r1-r2` written in travel order,
the drone "lands" back in `r1`, where it came from. `r1` is already visited, so the branch dies.

- Map 03 fails and map 04 (same map, connection written `r2-r1`) works.
- Map 12: the restricted lane is unusable, so all 8 drones queue on the normal lane (11 turns).
  Flipping one line in the file gives 9.
- `challenger/01` has restricted-restricted connections.

Reconstruction repeats the same guess for this case (lines 292-306), with a condition that
cannot work: `node not in allocation_table[turn - 1].values()` compares a `Node` with occupancy
counts (ints). It is always true, so it also always picks `nodes[0]`.

**Root cause:** direction is information the search has when the drone takes off and throws
away, then tries to rebuild from the zone types. The in-flight state should carry its
destination, or its origin, from the moment it is queued. E4 used the origin, recovered from
`prev_nodes`.

### 3.2 Time bookkeeping assumes every move takes one turn

The whole expansion is written around `turn` and `turn + 1`: capacity checks, reservations,
`visited` and `end_turn`. A restricted move spans three turns, and each needs a different
check:

| Turn | What must be free | What the code checks |
|---|---|---|
| t (take-off) | the connection | the connection at t (line 153) |
| t+1 (in flight) | the connection | nothing |
| t+2 (landing) | the restricted zone | nothing |
| - | - | the destination zone at t+1, twice: the general check (line 158) and the restricted check (line 189) |

Consequences:

- **P3 is broken** (05, 06, 07): landing at t+2 is never checked, so drones take off towards a
  zone that will be full when they arrive.
- **Take-offs are refused for the wrong reason**: the general check (line 158) refuses a
  take-off when the zone is busy during the flight turn, although the drone is not in the zone
  then. E6 shows the cost: map 05 goes from 7 to 5 turns, map 06 from 6 to 5.
- **Latent link overflow**: nothing checks the connection on the in-flight turn t+1. The
  reservations do hold the connection at t and t+1 (section 3.5), so a drone taking off at t
  and a drone planned earlier that takes off at t+1 could share a capacity-1 link on turn t+1.
  I did not observe it in fuzzing.

### 3.3 `visited` is set when a move is considered, not when it is made

`visited.add(next_node)` (line 175) runs before the restricted-zone check. When that check
refuses the take-off, the zone stays marked as visited, and the drone can never try it again
on a later turn. The wait rule (`can_wait and not all_visited`) then sees every neighbour as
visited and refuses to wait, so the search runs out of states.

This is currently hidden, because the restricted check almost never refuses (it reads the
wrong turn). E1 shows what happens as soon as the check is correct: 05, 06 and 08 go from
"valid but overlapping" to "Path not found". **Fixing the landing check alone makes things
worse**; the landing check (3.2) and this one have to be fixed together.

More generally, `visited` is keyed by zone, while the search runs over (turn, zone) states. It
works for 1-turn moves only because the first arrival at a zone is also the earliest possible
one, and a later arrival can always be replaced by waiting. Two things break that assumption:
waiting is gated by a heuristic and its capacity is never checked (report 0, section 4), and
restricted moves mark a zone two turns before the drone is in it.

### 3.4 The search stops when the goal is queued, not when it is reached

`drone.done = True` (line 209) is set as soon as the exit is a neighbour that passes the checks.
For a 1-turn move, queuing the exit and reaching it amount to the same thing. For a restricted
exit, the queued state is the flight, so the search stops one turn before the drone lands.
Reconstruction then starts from `(end_turn, exit)`, where `end_turn` is the take-off turn, and
no such key exists. This is map 10 (and about two thirds of the random-map failures, since the
generator often makes the goal restricted). E5 moves the stop to the moment the drone lands,
and every remaining random-map failure disappears.

The pop-time check `if current == map.exit_point: break` (line 119) was meant to be that stop
condition, but it never runs, because the search stops at push time first.

### 3.5 The landing zone is reserved twice

Reconstruction reserves every path element at its own turn, including the restricted zone when
the drone is in it. On top of that, lines 290 and 306 add another reservation of the restricted
zone at `turn + 1`, which is the same (zone, turn) pair. After one drone crosses a
`max_drones=2` zone, the table holds `r: 2` on the landing turn:

```
0 {'start-r': 1, 'start': 1}
1 {'start-r': 1}
2 {'r-goal': 1, 'r': 2}
```

This is harmless while nothing reads the landing turn. Once the landing check is correct, a
zone with capacity 2 accepts only one drone. E3 shows it: map 08 goes from 9 turns to 5.

The connection gets reserved on two turns in a similar way, once as the edge used by the
take-off and once as the in-flight state. That happens to match the "occupied during transit"
reading of the subject, but it is a side effect of how the `prev_nodes` tuples are shaped, not
a stated rule. It is worth making explicit.

### 3.6 Summary of causes

| Symptom | Cause | Section |
|---|---|---|
| `r1-r2` chains, map 12, challenger | in-flight state has no destination | 3.1 |
| P3 violations | landing turn never checked | 3.2 |
| Needless waits before take-off | general zone check applied at t+1 to restricted zones | 3.2 |
| Path not found once P3 is checked | `visited` set before the take-off is accepted | 3.3 |
| Restricted goal | search stops at take-off, not at landing | 3.4 |
| Capacity 2 zone takes 1 drone (once 3.2 is fixed) | landing reserved twice | 3.5 |

All six share one underlying pattern: the code treats a restricted move as a 1-turn move plus
special cases, instead of as a move with its own duration. A move that knows its origin,
destination, take-off turn and landing turn could drive all the checks, `visited`, the stop
condition and the reservations from that one description.

## 4. Unchanged since report 0

- Planning is still sequential and each drone takes its own earliest arrival
  (`solver/01_braess_cross`: 42 turns vs 23, `solver/02_selfish_detour`: 29 vs 16).
- Waiting in a zone is still not capacity-checked.
- **Fixed since report 0:** connections are now sorted by descending priority (`-priority`), so
  priority zones win ties.
- `from dis import Instruction` and `from platform import node` are unused (flake8 F401).

## 5. Suggested order

1. Give the in-flight state its destination (3.1).
2. Rework the take-off checks as one unit: check the connection at t and t+1 and the zone at
   t+2, drop the t+1 zone check for restricted destinations, and only mark the zone visited
   once the take-off is accepted (3.2, 3.3).
3. Stop the search when the goal is reached, not when it is queued (3.4).
4. Remove the extra landing reservation (3.5).
5. Re-run `data/maps/claude/restricted/`. The expected turn counts in the README are the
   ones measured after E6.

The experimental copies are in the session scratchpad only. They were built to isolate causes,
not as proposed code.
